#+title: Project सत्र

* Overview
Project सत्र (Sattra) is an open-source patient management application for
small and medium clinics. It is a desktop application built with Flutter and
Dart, using Microsoft's Fluent design language, and it keeps a clinic's records
in a single SQLite file on the clinic's own machines.

It runs offline by default. Nothing is sent anywhere unless a clinic
deliberately connects its terminals to a hub on its own network.

* Features
- Patient register with the clinic's own intake form, including the nine-row
  symptom grid (sleep, bowel, appetite, digestion, stress, micturition,
  tolerance, menstruation, LMP)
- Consultations that record the symptom grid each visit, so change over time
  is visible
- Formulary and stock control, with a movement ledger and reorder warnings
- Prescriptions with OD/BD/Hs/TDS/EOD dosing, suggested quantities, and
  dispensing that deducts stock
- Appointment diary with clash detection and per-clinician filtering
- Staff records, two roles (Administrator, Healthcare Provider), and an
  activity log that attributes every change
- Printable case sheets, prescription slips, day schedules and stock reports
- Encrypted backups, CSV import of an existing register, and LAN sync between
  clinic terminals

* Getting started
Requires the Flutter SDK (stable) and a desktop toolchain for the target
platform.

#+begin_src bash
flutter pub get
flutter run -d linux     # or: flutter run -d windows
#+end_src

On first launch the application asks for the clinic name, how this machine is
used, and the first administrator account.

** Trying it with sample data
#+begin_src bash
dart run tool/seed_demo.dart demo-data
SATTRA_DATA_DIR=$PWD/demo-data flutter run -d linux
#+end_src

=sattra123= (provider). Settings has a *Delete records* section for clearing
the sample data out again before going live.

* Deployment
Each installation is one of three things, chosen during setup and changeable
later in *Settings → Clinic network*:

| Role      | What it does                                                       |
|-----------+--------------------------------------------------------------------|
| Standalone | Keeps its own records. No networking.                             |
| Clinic hub | Holds the clinic record and serves the other terminals.           |
| Terminal   | Keeps a full working copy and syncs it with the hub.              |

The hub generates a *clinic key*. Every terminal is given the same key; it
encrypts all traffic between machines and is what admits a machine to the
clinic network. A short fingerprint is shown on each machine so two terminals
can be checked against each other without either screen displaying the key.

** How sync works
Terminals push their own unacknowledged changes, then pull everything newer
than their last watermark. Conflicts are resolved last-write-wins, with ties
broken deterministically on the originating node id, so two machines resolving
the same conflict independently reach the same answer. Deletions are
tombstoned rather than dropped, so a removal propagates instead of the row
reappearing on the next sync.

Sync runs every two minutes, immediately after signing in, and on demand.

** Where passwords live
Password verifiers exist only on the hub. They are in tables that are not part
of the replicated set, so they physically cannot leave that machine through a
sync.

A terminal signs a user in by asking the hub. On success it caches a verifier
for *that user on that machine only*, derived under its own random salt, so
the user can still work if the hub is unreachable later. No terminal ever ends
up holding the clinic's whole password file.

That cached verifier is deliberately short-lived:

- Changing a password bumps the staff record, which replicates. A terminal
  refuses any cached verifier older than the staff record it belongs to, so a
  reset password stops working offline as soon as the record reaches that
  machine.
- A verifier is refused outright after 30 days without a successful hub
  sign-in.
- A hub that answers and *refuses* a sign-in is final. Only an unreachable hub
  allows the offline path, so a terminal can never overrule a live rejection
  with an older cached decision.

** What the clinic key does and does not do
The clinic key decides which *machines* may talk to the hub. It says nothing
about who is sitting at one, so the hub authorises every write on its own:

- Staff records may only be pushed by an administrator. They carry the role
  that authorisation itself reads back, so accepting one from a provider would
  let them promote themselves.
- The activity log is append-only for everyone. New entries are accepted;
  edits and deletions of existing ones are refused.
- Column names in a sync payload are filtered against the real database schema
  before any statement is built, so a crafted field name cannot become SQL.

* Data
Everything lives in one SQLite file. *Settings → Storage* shows its size, what
it contains, and lets an administrator move it elsewhere.

- *Backups* are a single encrypted file protected by a passphrase the
  administrator chooses. They include staff accounts, so a restored machine can
  sign people in on its own.
- *Import* reads patients or the formulary from CSV. A filled-in sample file
  can be downloaded from Settings to show the expected format; only =name= is
  required, and column order and heading style do not matter.

lib/
  core/        constants (the clinic's own vocabulary), formatting, ids
